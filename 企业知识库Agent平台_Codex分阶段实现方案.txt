企业知识库 + Agent 智能体平台
Codex 分阶段实现方案
============================================================

一、项目定位
------------------------------------------------------------
项目名称：Enterprise AI Hub（可自行改名）

目标：
实现一个支持多租户、企业知识库、RAG 问答、Agent 工具调用、工作流编排、
模型统一接入、用量统计和审计日志的 AI 应用平台。

第一版不要做成 Dify 的完整替代品。
第一版只完成一个闭环：

管理员创建企业
→ 创建知识库
→ 上传文档
→ 系统解析、切片、向量化
→ 创建智能助手
→ 绑定知识库和模型
→ 用户发起对话
→ 系统检索知识
→ 大模型生成带引用的答案
→ 记录 Token、耗时、检索结果和审计日志

第二版再加入：
Agent 工具调用、工作流、企业业务接口、审批机制、计费套餐、开放 API。

适用场景：
1. 企业内部知识库
2. 产品说明书问答
3. 售后客服
4. 技术文档助手
5. 合同或资料分析
6. 企业业务查询助手
7. 面向客户发布的网页 AI Bot

三、关键架构原则
------------------------------------------------------------
1. Workflow 和 Agent 分开
Workflow 是确定性流程，路径由代码控制。
Agent 是动态流程，由模型选择工具。
能用 Workflow 解决的任务，不要直接交给 Agent。

2. 模型与业务隔离
所有模型统一经过 Model Gateway。
业务模块只依赖统一接口，不依赖某个厂商 SDK。

3. 长任务异步化
文档解析、切片、Embedding、批量重建索引必须进入 BullMQ。
HTTP 请求只负责提交任务并返回 jobId。

4. 所有数据都带 tenantId
数据库表、缓存 key、对象存储路径、队列任务必须带 tenantId。
禁止只依赖前端传来的 tenantId，后端必须从认证上下文解析。

5. Agent 工具默认无副作用
查询类工具可自动执行。
写数据库、发邮件、创建订单、删除文件等工具必须进入人工审批。

6. 结果必须可追踪
每次回答记录：
- 用户输入
- 使用的模型
- Prompt 版本
- 检索文档及分数
- Tool 调用
- Token 用量
- 首 Token 时间
- 总耗时
- 错误
- 最终回答
- traceId

7. RAG 回答必须提供引用
引用至少包含：
- documentId
- 文档名称
- chunkId
- 页码或段落
- 摘要
- 检索分数

8. 安全优先
- 禁止任意 URL 请求
- 禁止任意 SQL
- 禁止任意代码执行
- 禁止模型直接获得数据库凭据
- Tool 必须白名单注册
- Tool 输入必须经过 Schema 校验
- Tool 必须有超时、并发限制和审计

七、RAG 处理流程
------------------------------------------------------------
文档导入：
1. 用户上传文档
2. API 校验类型、大小、租户权限
3. 计算 SHA-256，检查重复
4. 原始文件保存到 S3/MinIO
5. 创建 documents 记录
6. 提交 document.parse 队列任务
7. Worker 提取文本和文档结构
8. 清理页眉、页脚、空白和乱码
9. 按标题、段落和 Token 进行切片
10. 提交 document.embed 队列任务
11. 批量生成 Embedding
12. 写入 document_chunks
13. 创建或更新向量索引
14. documents.indexStatus = ready

默认切片参数：
- chunkTokens：800
- overlapTokens：120
- minChunkTokens：80
- 保留标题
- 保留页码
- 表格尽量作为完整块保留
以上必须可在知识库级别配置。

查询：
1. 校验用户和 assistant 权限
2. 对问题进行规范化
3. 生成查询向量
4. 向量召回 Top 30
5. PostgreSQL 全文召回 Top 30
6. 合并并去重
7. 使用 RRF 或加权评分融合
8. 可选 rerank，保留 Top 8
9. 根据 Token 预算组装上下文
10. 调用模型
11. 校验引用是否真实存在
12. 返回答案和引用

禁止：
- 模型捏造不存在的 documentId
- 将整个文档无上限塞入上下文
- 不经过 tenantId 过滤进行向量搜索


八、Agent 工具系统
------------------------------------------------------------
Tool 接口：
- name
- description
- inputSchema
- outputSchema
- permissions
- sideEffectLevel
- timeoutMs
- execute(context, input)

内置工具：
1. knowledge_search
2. current_user
3. current_time
4. http_request_whitelist
5. readonly_sql_template
6. get_product
7. get_order_status
8. create_support_ticket，需审批
9. send_email，需审批

安全规则：
- HTTP Tool 仅允许访问配置好的域名
- 禁止内网地址、localhost、metadata 地址
- SQL Tool 不接收模型生成的原始 SQL
- SQL Tool 只能选择预定义 queryId 和参数
- 所有 Tool 输出限制最大长度
- Tool 超时后必须中断
- Tool 调用次数默认最多 8 次
- Agent 总运行时间默认最多 60 秒
- 写操作必须带 idempotencyKey
- 有副作用工具必须人工批准后执行

  ↓

- input

工作流节点必须：
- 输入输出有 Schema

- 支持重试策略
- 支持 traceId
- 支持超时
- 失败时给出明确错误类型

十六、最重要的实施顺序
------------------------------------------------------------
不要先做漂亮 UI。
不要先做拖拽工作流。
不要先做多 Agent。
不要先接十几个模型。
不要先做支付。

正确顺序：
数据隔离
→ 模型网关
→ 文档索引
→ 检索质量
→ 流式问答
→ 引用可信
→ Agent 工具
→ 人工审批
→ 工作流
→ 用量和商业化

RAG 产品最容易翻车的地方不是页面，而是：
1. 文档解析质量
2. 切片质量
3. 召回质量
4. 引用真实性
5. 多租户隔离
6. 异步任务幂等性
7. 模型调用成本
8. Agent 工具权限

先把这八项做硬，产品才不是一个“套壳聊天框”。
